> **Abstract:** every control on the platform, each linked to the adversary it
> answers, the code seam that enforces it, and the ADR that decided it — the
> "does it cover this threat?" self-check. **Who is it for:** the developer
> adding a feature and the auditor verifying a control holds. **When to read
> the rest:** before adding a data class or privilege surface — add a row here
> and in the [adversaries](adversaries.md) table before merge.

## 5. Control map — every threat must be covered

Quick self-check when adding a feature: does it introduce a new data class or a new
privilege surface? If so, add a row here and in the relevant checklist.

The **Seam** column names the code file / class that enforces the control — or,
where the control is an owner-ops step (a flag, a daemon, a documented default, a
runbook step) rather than a unit-tested code path, the runbook that documents it.
The **Pinned by (test)** column names the existing test that pins a code seam
(class + method — the most load-bearing ones); an owner-ops row is marked
`— (owner-ops, no code seam)`, since it has no code seam to pin. The **ADR**
column names the ADR that decided the control, or links the
[`decisions`](decisions-open-items.md#decisions) entry. These are the stable
keys a later change must not silently break.
