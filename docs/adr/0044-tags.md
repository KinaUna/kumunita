# ADR 0044 — Tags: free author-set subject labels for posts and blog pages (TG)

Status: Accepted
Date: 2026-09-19

Builds on the frozen base of **0004** (Marten doc ownership + additive
schema-evolution, §B.1 — the `TagIds` field is an additive doc field exactly
as `Post.Status` / `GroupId` / `LanguageCode` and `Post.ImageIds` are), **0005**
(the multilingual seam — a tag's display name is resolved the same
preference → default → `en` way a `PostTranslation` name is), **0013** (the
group-post lane — tags ride the shared `Post` doc, so the one `TagIds` field
covers both community and group posts), **0022** / **0026** (the
user-added-translation idiom — `TagTranslation` is `GroupTranslation` minus
`Description`), **0025** (the `ImageIds` many-valued-id idiom the `TagIds`
field mirrors), **0039** / **0040** (the `Page` + `PageKind` model — tags
attach to `PageKind.User` blog pages only), and **0011** (the shared-id-doc
context shape — `MediaObject` referenced by many owners is the model for a
`Tag` referenced by `Post` and `Page`). No amendment to 0004, 0005, 0013,
0022, 0026, 0025, 0039, 0040, or 0011 — this ADR is additive on their
decisions exactly as written.

This ADR is the **sign-off gate** of the `TG` (Tags) named lane — the lane
plan is `plans-milestones/in-progress/tags/plan-tags.md`. Every later `TG`
unit (U01–U05) codes against the *locked* text here; changing a decision
below requires an amendment, not a unit-level override.

## Context

A resident who wants an overview of "everything we've posted about
`sanitation`" or "`budget`" has no way to get it. The platform organizes
content by **Component** (a *feed* — Safety, Maintenance, Social, Governance;
one per post, a posting-membership boundary), by **Group** (a *membership
channel*; one per post, the access gate), and by **author**. None of those
expresses *what a post is about*. A post about the Maple Street flood is
simultaneously Safety and Maintenance and Social — but it lives in exactly
one Component, and none of the Group lanes apply. There is no primitive that
says "this post is *about* several subjects at once" without any of them
becoming an access boundary.

The platform also has no **tag vocabulary**: there is no way to see what
subjects residents are actually posting about, or to browse *by* subject.
The two are the same gap — the absence of a lightweight, multi-valued,
non-access organizational label.

Tags are that label. They are deliberately **not** a new organizing *surface*
in the way a Component is: they grant no membership, no access, no
moderation scope. They are *edges between existing content* that no other
mechanism draws. That is the integration payoff in the philosophy's terms
(the value is the linkage, not the parts), and it is why the whole feature
can be built additively on top of the frozen access model without touching
it.

**What this is, in one line:** any author may attach a small set of free
subject labels to their own post or blog page; a label's display name can
carry a per-language translation set by the label's creator; and a resident
may browse "all my content tagged `X`" and "all tags I can see" and get
autocomplete as they type — all computed over content the resident may
already read, so a tag never leaks the existence of a subject behind content
they cannot see.

## Decision

### D1 — Two new documents in a new `Kumunita.Core.Tags` context

`Tag` is a **shared id-doc referenced by two other contexts** (`Post`,
`Page`) — exactly the ADR 0011 `MediaObject` shape (referenced by `Post`,
`Announcement`, `Profile`, `LocalizedPage` via `ImageIds` / `AvatarId`). It
therefore lives in its **own context**, `Kumunita.Core.Tags`, not inside
`Posts` or `Pages` (a tag is not a post's private data; it is a first-class
organizational primitive two contexts share, just as a media object is).

- **`Tag`** — `Id` (surrogate PK, the Marten identity), `Slug` (the
  **business key** — the label's language-neutral identity, D3), `Name` (the
  **base** display name — the creator's own spelling), `LanguageCode`
  (the BCP-47 code the creator **authored** it in, ADR 0018's
  authored-in idiom; the base language), `CreatedBy` (the subject id of the
  actor who created it — the translation standing owner, D4), `Created`.
- **`TagTranslation`** — `Id` (surrogate PK), `TagId` (the parent `Tag`),
  `LanguageCode` (the language this name is **in**), `Name` (the translated
  display name), `AuthorId` (the creator, D4), `Created`. This is
  **`GroupTranslation` (ADR 0026) minus `Description`** — a tag has a name
  only, no description.

Both register in a **new `TagDocTypes`** surface (mirroring
`MediaDocTypes`), with a **`UniqueIndex` on `(TagId, LanguageCode)`** — the
same business-key convention as `GroupMembership` / `PostTranslation`
(surrogate `Id` is the Marten identity, the pair is the DB-enforced business
key; at most one translation row per tag per language, re-adding overwrites).

**`Tag` carries no `Audience` and no standing surface of its own** — the
ADR 0022 / 0026 read-pin carried over: a tag row has no own visibility; its
visibility is *derived* from the content that references it (D5). A tag used
only on content a viewer cannot read simply never surfaces to them.

### D2 — `TagIds` is an additive field on `Post` and on `Page`

- **`Post.TagIds`** — `string[]` (default empty), registered in
  `M3DocTypes`. This is an **ADR 0004 §B.1 additive field** — delta-detected,
  idempotent, no re-seed, no EF migration — exactly the `Post.Status`
  (M3b), `Post.GroupId` (ADR 0013), `Post.LanguageCode` (ADR 0018), and
  `Post.ImageIds` (ADR 0025) history on the POCO. Because **community and
  group posts share the `Post` doc** (ADR 0013), this one field tags **both**
  lanes; there is no group-specific field and no reply field.
- **`Page.TagIds`** — `string[]` (default empty), registered in the `Page`
  doc type. Populated **only on `PageKind.User` (blog) pages** (D6); a
  `PageKind.System` page's `TagIds` is **always empty** (the shape permits
  it, the write lane refuses it).

**Not-in-scope (locked, D8):** `TagIds` is **not** added to `PostReply`
(replies are excluded by the author), **not** to `Announcement`, and is
**refused on `PageKind.System` pages** (D6). A tag is a post- or blog-page
label, nothing more.

### D3 — A tag's identity is a language-neutral `Slug`; the name is display

The tag's **business key is `Slug`** — a language-neutral identifier, not a
display string. The `Name` (and `TagTranslation.Name`) are **display**
values, resolved per-viewer (D4 display). This is the one decision that
keeps translation a *solved* problem rather than a sprawl generator: a tag
is **one document with per-language names**, **not** N near-duplicate tags
one per language.

**`Slug` is the literal string the author typed, lowercased and trimmed —
not** URL-canonicalized, accent-folded, or cross-language-merged. So if one
author types `sanitation` and another types `Hygiène`, those are **two
separate tags**, both valid, both visible in the tag list. This is the
deliberate "a small user base can live with some inconsistent tags; the
community can discuss confusing ones among themselves" trade the author made,
and it is the reason D8 has **no** merge/rename lane (a merge is a future
lane *if* it ever becomes a problem — it is not needed to make the feature
work, and building it now would be the premature part the philosophy warns
against).

A `Slug` is validated to a small safe charset (letters, digits, hyphen,
underscore; ≤ 64 chars) so it is safe to round-trip through a URL
(`/tags/{slug}`) and to store in `TagIds`. The write seam derives it from
the author's typed string; the author does not type a slug directly.

### D4 — Standing: attach is free; a tag's *translations* belong to its creator

Two different actions involve typing a tag name, and they get different
standing (the ADR 0006-D "the service owns the decision, not the Web" rule):

- **Attach** (add a tag to *your* post / blog page) — **free, per the
  author's rule.** It is the object's existing **edit standing**: the post's
  author (ADR 0014 / 0016 author-only lane; group-post author, ADR 0013) or
  the blog page's author ∪ GlobalAdmin (ADR 0040). Attaching a tag is part
  of editing that object's body; it is not a separate privilege. If the
  `Slug` does not yet exist, it is **created** and the attaching author
  becomes its `CreatedBy` (their typed spelling becomes the base `Name`).
- **Translate** (add / overwrite a `TagTranslation` for an existing tag) —
  **the tag's `CreatedBy` ∪ GlobalAdmin only**, an `AccessVia.Owner` /
  `AccessVia.Admin` audit tag. A later author who *attaches* the tag to
  their own post **does not** get to reword the tag's display name: the
  creator is the one who read the content and chose the name, and rewording
  changes what **everyone** in that language sees. This is the same
  "the name is the creator's artifact" rule as ADR 0009 (a group's name is
  the owner's, not a member's) and ADR 0026 (a group/community name is the
  owner's / GlobalAdmin's, not a member's) — carried to tags.

  The author's stated reasoning — *the post author is the only one in a
  position to judge what the tag means, because admins/translators may not
  have access to the content* — is realized as **the creator** (the author
  who attached it first and read the content) owning the translations, not as
  "any attacher may retranslate." A GlobalAdmin may still reword any tag
  (the break-glass standing), but no *arbitrary* attacher may.

Standing is resolved in Core (a `TagService` write seam), never from a UI
affordance. Two public display probes mirror `PostService.CanAddTranslation`:
`TagService.CanAttachToPost(post, actorId, actorRoles)` and
`TagService.CanTranslateTag(tag, actorId, actorRoles)`.

### D5 — One read seam; the tag list, "by-tag," and autocomplete all derive from it

There is **one load-bearing read contract**, and the three surfaces (tag
list, "posts/pages tagged X", autocomplete) are all callers of it:

> **the base query:** the set of `Tag` rows used on **at least one**
> `Post` / `PageKind.User` `Page` that the **viewer may already read**.

- **Tag list** ("what subjects exist") — `TagService.ListForActorAsync`:
  distinct tags from the base query, with a use-count and the display name
  resolved to the viewer's language (D4 display).
- **"Posts / blog pages tagged `X`"** — `TagService.ListPostsByTagAsync` /
  `ListPagesByTagAsync`: the readable posts/pages whose `TagIds` contains
  that tag. A post that carries the tag but is **not** readable by the
  viewer is excluded (the post's own `Read` decision is the gate — the tag
  grants nothing).
- **Autocomplete** — `TagService.SuggestAsync(prefix, actor)`: the base
  query filtered by **`starts_with(displayName, prefix) OR
  starts_with(slug, prefix)`**, capped (≤ 10), where `displayName` is the
  name resolved **in the viewer's language** (a `de`/`fr`-speaking user
  typing `hy` gets `hygiène` even if the `Slug` is `sanitation`).

**Privacy is structural, not a per-surface check.** Because the base query
is already scoped to "content the viewer may read," a tag used only behind
content the viewer cannot read **never appears** in the tag list, in the
by-tag results, or in autocomplete. A private family group's internal tag is
invisible to a non-member. This is what keeps rule 4 ("tags do not touch
access") from leaking a *subject's existence* — the tag grants nothing, and
it also reveals nothing. (A global tag enumeration, by contrast, would leak
"the topic `divorce` exists on this instance" to every visitor — that is
excluded by design.)

**Display resolution** reuses the existing preference order (the
`ITranslationProvider` / ADR 0005 idiom): the viewer's preferred language →
the `TagTranslation` for that language → the tag's base `Name`. Nothing new
is built; a tag's name resolves exactly the way a `PostTranslation` name
does.

### D6 — `PageKind.User` (blog) pages only; `System` pages are out

Tags attach to **blog pages** (`PageKind.User`, ADR 0040) — a resident's
personal knowledge pages are exactly the "a resident's 'our garden project'
page should be tagged `garden` + `sanitation`" case. **`PageKind.System`
pages are not taggable** (D2): About / Terms / Help / Privacy / Conduct
*are* their subject (they are platform chrome, authored by the operator,
ADR 0040 / 0043), not *about* a resident's subject — tagging them with
`budget` is incoherent. The write seam refuses `TagIds` on a `System` page
(the `TagIds` field is present on the `Page` doc shape for the additive
pattern, but the `System`-kind lane rejects a non-empty value).

### D7 — Auditing and consistency

- **Attach / create / translate** writes resolve standing (→
  `UnauthorizedAccessException` when denied) and, on success, write a
  hand-written `AccessAudit` row in the caller's session, single
  `SaveChangesAsync` (the C3 idiom): `tag.attach` (`TargetKind = "post"` /
  `"page"`), `tag.create` (`TargetKind = "tag"`), `tagtranslation.add`
  (`TargetKind = "tag"`). `Via` = `Owner` (author / creator) or `Admin`
  (GlobalAdmin).
- **Reads** (`ListForActorAsync`, `ListPostsByTagAsync`,
  `ListPagesByTagAsync`, `SuggestAsync`) are plain reads with **no
  authorization gate of their own and no audit row** — the row is only ever
  rendered on a surface that already required the referenced content's reach
  (the ADR 0022 / 0026 "a read, not a decision" pin, C-M3·1 carried over).
  The access decision is the *content's* existing `Read`, not the tag's.
- **Detach** (remove a tag from a post/page) is part of the same edit lane
  as attach (re-saving the object's `TagIds`), same standing, same audit
  family. **Deleting a `Tag` doc** is **not** a lane (D8) — a tag whose
  content is all removed is simply no longer reachable by the base query;
  there is no explicit "delete tag" seam.

### D8 — Not-in-scope (locked)

- **No tag merge / rename lane.** `Slug` is the literal typed string (D3);
  two similarly-intended tags stay two tags. A merge/rename is a *future*
  lane if the community actually needs it — building it now would be a
  premature part with no closed loop.
- **No tag-based access.** A tag grants no membership, no read, no
  moderation scope, on any object. The tag is a label, never a gate (rule 4).
- **No tagging on replies, announcements, or `System` pages** (D2 / D6).
- **No tag moderation, no tag reporting.** A tag is not a content surface
  with a moderation lane; a confusing tag is discussed by residents
  (D3 / D8).
- **No seeded / curated default tags.** Free-for-all (rule 3) — there is no
  seeder row, no "suggested tags" pack, no admin tag management surface
  beyond the GlobalAdmin break-glass standing in D4.
- **No machine translation** of tag names (ADR 0005 §C — the boundary this
  repo keeps out of scope; a tag translation is a human-set display name,
  like a `GroupTranslation`).
- **No tag-count threshold / auto-pruning / usage analytics.** The
  use-count in `ListForActorAsync` is a display aid, not a moderation
  signal.

## Consequences

- **Additive, no migration.** `Tag` / `TagTranslation` are new doc types
  (new `TagDocTypes` surface, ADR 0004 §B.1 — idempotent, delta-detected);
  `Post.TagIds` / `Page.TagIds` are additive fields (ADR 0004 §B.1, no EF
  migration — the `mt` schema is Marten-owned). `M4/M5/M6` stay Events /
  Projects / Portability; the `TG` lane is a **named lane**, not a new
  M-letter (the ADR 0013 `GP` precedent).
- **The access model is untouched.** No new `AccessAction`, no new
  `AccessVia` value beyond the existing `Owner` / `Admin` used for audit, no
  new `Decide()` branch, no audience surface on a tag. The single
  load-bearing contract stays the *content's* existing `Read` decision; the
  tag is computed over it, not a gate of it. This is why the feature can be
  built without reopening ADR 0006.
- **The privacy model is strengthened, not weakened.** The scoped base query
  (D5) means a tag never reveals the existence of a subject behind content
  the viewer cannot read — the opposite of a naive global tag cloud. This is
  a direct `SECURITY.md` win: the tag surface is a *consequence* of existing
  access, never a new leak vector.
- **Inconsistency is a deliberate, bounded cost.** Free `Slug`s (D3) mean
  near-duplicate tags are possible (`sanitation` / `sanitation-2`); the
  accepted trade is that a small resident base can live with and discuss
  that, and a merge lane is deferred until there is a closed loop that needs
  it. If it becomes a real problem, the D8 not-in-scope list is the place to
  lift it — deliberately, with an owner and a response (principle 6), not by
  accretion.
- **`Post.TagIds` on group posts is a small surface area that must be
  honored by the ADR 0013 lane exclusivity.** A group post's `TagIds` do not
  make it appear in any non-member's "by-tag" view (the base query is
  scoped to readable content — D5), and do not make it appear in any feed
  (the ADR 0013 lane exclusivity is unchanged — the tag is a label, not a
  feed). The by-tag read must apply the post's **own** access decision
  (audience for community posts, membership for group posts) *before*
  returning it, exactly as the ADR 0035 `PostReadDecision` shared routing
  seam already does for media.
