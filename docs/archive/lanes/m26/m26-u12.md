## Understanding

This unit applies the **U10 `_Sort` pattern** to the **projects** surfaces —
the todos list (`TodosIndex` → `TodoIndexViewModel`), the boards list
(`BoardsIndex` → `BoardIndexViewModel`), and the projects+goals landing
(`ProjectsIndex` → `ProjectsIndexViewModel`, which renders **two** paged
sections: goals via `PagerGoals` and projects via `PagerProjects`) — the view-
model `Sort` field + the `@Html.Partial("_Sort", ...)` + the pager-carry + the
`SortSpec` threading — with the **pinned Web tests** (U2 §2.6). **Reuse U10's
`SortViewModel`/`_Sort` verbatim — do not fork.** **Note:** the `ProjectsIndex`
surface has **two** pagers (goals + projects) — each gets **its own** `Sort`
field + **its own** `Options` (C-SORT·1/F9), mirroring the `PagerGoals`/
`PagerProjects` dual shape.

## Rules
- **Reuse** U10's `SortViewModel`/`_Sort` verbatim (C-SORT·1 — each surface
  passes **its own** allowed-key `Options`; the todos' `due`/`priority`/
  `status` keys are offered in **the todos surface's** `Options` only, F9).
- **C-SORT·8** — each surface's pager carries **its own** `sort`/`dir`.
- **C-SORT·2** — the `null`/no-sort pin is unchanged.
- **C-SORT·4** — authorization is **untouched**; the existing filters
  (assignee/project/blocked) are **frozen** and still carried on the pager.
- **Do not** touch the kanban **column** order (named non-decision).
