## The state of the code (measured 2026-11-11, `development`)

- **What a "lead" is** — `count_a11y()` in `tools/ux/ux-measure.py`. A lead is
  a non-`hidden` `input`/`select`/`textarea` that has **none** of:
  `aria-label`, `aria-labelledby`, (`id` present **and** in some `<label
  for="…">`), or an open `<label>` ancestor (R23). Every `<img>` without an
  `alt` is also a lead.
- **The leads in this batch** — 7 total, **all unlabeled controls** (no
  missing-`alt` images in this batch). Per view: `Document/Index` **1**,
  `Profile/Edit` **4**, `Guardian/Detail` **1**, `Guardian/Index` **1**;
  `Document/Edit`, `Document/New`, `Directory/Index`, `Profile/Preview` are
  **0** (already clean — read them to confirm, then move on; no edit expected).
- **The leads here are NOT the plain "sibling-label-without-`for`" shape**
  (the R24/R25/R26 idiom). There are three distinct cases, and two of them
  look like they should already be fine. Get these right or you will (a)
  "fix" a control with an `aria-label` to dodge the real fix, or (b) introduce
  a duplicate `id` and silently break the runtime association.

## The work

Work view-by-view; after each, re-run the per-view measure (see *Before
committing*) to confirm that view is at 0 before moving on.

### Shape 1 — `asp-for` inputs whose `id` only exists at render time (4 leads)

**`Profile/Edit.cshtml` (4):** `DisplayName` (line ~102), `Email` (line ~107),
`Address` (line ~170), `Phone` (line ~179). Each is a TagHelper-bound
`<input asp-for="…">` that already has a correct sibling `<label for="…">`
(e.g. `<label for="DisplayName" …>` above `<input asp-for="DisplayName" …>`).

**Why it is still flagged:** the `id` on an `asp-for` input is **generated by
the TagHelper at render time** — it is not literal in the `.cshtml` source.
`count_a11y()` is a *static* source analyzer, so it sees the `<label
for="DisplayName">` but no `id="DisplayName"` in the text, and flags the input.
At runtime the label is **already** correctly associated; this is the one place
in this batch where the accessibility is already correct and only the static
check disagrees.

**Fix:** make the association visible in source by adding the explicit
`id` attribute that `asp-for` would emit anyway —
`<input asp-for="DisplayName" id="DisplayName" …>`, and the same for `Email`,
`Address`, `Phone`. This is a **harmless redundancy** (the rendered output is
identical — `asp-for` sets the same `id` by default), not an `aria-label`
dodge. No new string, no markup restructure. Do **not** add an `aria-label`
here — the real `<label for>` is the correct mechanism.

### Shape 2 — checkbox with a sibling `<label>` that has no `for` and no `id` (2 leads)

**`Guardian/Detail.cshtml` (1):** the delete-child confirm checkbox —
`<input name="Confirmed" type="checkbox" …>` (line ~512) sits above a
`<label class="form-check-label">` with **no `for`** (line ~513), and the
input has **no `id`**.
**`Guardian/Index.cshtml` (1):** the accept-terms consent checkbox —
`<input name="GuardianConsent" type="checkbox" value="true" …>` (line ~100)
above a `<label class="form-check-label">` with **no `for`** (line ~101), no
`id`.

**Fix:** give each input a unique `id` and add the matching `for` to its
existing `<label>`. Suggested ids:
- `Guardian/Detail`: `id="delete-child-confirmed"`.
- `Guardian/Index`: **do NOT reuse `GuardianConsent`** — a second,
  already-correct input further down the same file uses `id="GuardianConsent"`
  (line ~206, the paired `for="GuardianConsent"` one). Reusing that id here
  would create a **duplicate id in one document** and point both labels at the
  wrong control. Use a distinct id, e.g. `id="accept-consent"`.

### Shape 3 — a control with only a placeholder and no `<label>` (1 lead)

**`Document/Index.cshtml` (1):** the "New folder" name field —
`<input class="form-control" type="text" name="Name" … placeholder="…">`
(line ~67), inside a `<details>/<summary>` form. It has **no `<label>` at
all** — only a `placeholder` (the `documents.folder_name_placeholder` key) and
the "Create" submit button. A placeholder is not a valid accessible name
(WCAG 1.3.1: it disappears on input), so this is a genuine gap, not a static
artifact.

**Fix:** give the input an `id` (e.g. `new-folder-name`) and add a real
`<label>` for it. Because the `<summary>` ("New folder") + placeholder already
provide visible context and a visible label would change the layout, a
**visually-hidden** label is appropriate here:
`<label class="visually-hidden" for="new-folder-name"><kw-l key="documents.folder_name_placeholder">…</kw-l></label>`
(reuses the existing placeholder key — **no new translation string**). This is
the one case in this batch where a `<label>` element is *added* rather than
just paired. Keep it inside the existing `<form>` so it still submits with the
field.

## Before committing

```bash
# per-view — each of the eight named views must report 0 unlabeled + 0 img-missing-alt
python3 -c "
import importlib.util
spec = importlib.util.spec_from_file_location('uxm','tools/ux/ux-measure.py')
m = importlib.util.module_from_spec(spec); spec.loader.exec_module(m)
def measure(name):
    f = m.ROOT/'src/Kumunita.Web/Views'/name
    col = m.TagCollector(); col.feed(m.strip_comments(f.read_text()))
    bad = [c for c in col.controls if c.get('type','').lower()!='hidden'
           and not (c.get('aria-label') or c.get('aria-labelledby') or (c.get('id') and c['id'] in col.labels_for) or int(c.get('_label_depth','0'))>0)]
    return len(bad), sum(1 for i in col.images if 'alt' not in i)
for v in ['Document/Edit.cshtml','Document/New.cshtml','Document/Index.cshtml',
          'Directory/Index.cshtml','Profile/Edit.cshtml','Profile/Preview.cshtml',
          'Guardian/Detail.cshtml','Guardian/Index.cshtml']:
    print(v, measure(v))
"
python3 tools/ux/ux-measure.py            # total a11y dropped by exactly 7 (63 -> 56)
python3 tools/ux/ux-measure.py --check    # MUST pass
```
