# M20 · U05 — Web: `NotificationFlushHandler` + `NotificationFlushTick` + `Program.cs` seed

**Lane:** Web. **Depends on:** U02 (evaluator), U03 (`EmailDeferred` + `DeferredKey`), U04 (`FlushAsync` service + `QuietCheckMinutes` seam + admin setter). **Test assembly:** Web.Tests.

## Goal

Wire the **durable flush job** into the Web host: a self-rescheduling
Wolverine tick (`NotificationFlushTick`) whose handler calls U04's
`NotificationFlushService.FlushAsync`, then re-schedules the next run at the
**resolved admin cadence** (`QuietCheckMinutes`, 5–1440 min). Seed the first
tick in `Program.cs` after host start, alongside the existing three §6.4
jobs.

This is the "last mile" of the flush lane: U04 built the Core service
(Wolverine-free, testable in-process); U05 makes it **run on a schedule**
in the Web host.

## Deliverables

### 1. `src/Kumunita.Web/SideEffects/NotificationFlushHandler.cs` (new file)

Mirror the `EventReminderHandler` shape (static class, one `Handle` method,
the tick record at the bottom) with one **critical difference**:

- **The handler resolves the admin cadence at each run** and re-schedules
  using that value, **not** the baked `TimeoutMessage` delay.
- The baked `TimeoutMessage` delay is a **sensible default** (60 min, matching
  `QuietCheckMinutes` default) used only for the **first-boot seed** in
  `Program.cs`. Steady-state cadence is always the resolved admin value.

```csharp
using Kumunita.Core.Notifications;
using Kumunita.Core.Localization;
using Kumunita.Core.UserInfo;
using Kumunita.Core.Identity;
using Marten;

namespace Kumunita.Web.SideEffects;

public static class NotificationFlushHandler
{
    public static async Task<IEnumerable<object>> Handle(
        NotificationFlushTick tick,
        IDocumentStore store,
        IMailerStage mailer,
        ILocalizationService localization,
        ITranslationProvider translationProvider,
        IUserInfoService userInfo,
        // M20 (U04) — the Core notification service, injected ONLY to read
        // the resolved admin cadence (GetQuietCheckMinutesAsync, which floors
        // a missing LocaleSettings row to 60). The EventReminderHandler
        // precedent injects NotificationService the same way (to forward the
        // emitter); here we use it for the D6 read seam.
        NotificationService notifications)
    {
        // Flush all due deferred emails (U04's Core service). Note the exact
        // FlushAsync signature (U04, verbatim): (store, now, mailer,
        // ILocalizationService, ITranslationProvider, IUserInfoService, ct) —
        // there is NO IOptions parameter (M20 reads its cadence from the
        // LocaleSettings singleton, not a config POCO — the D6 shape, unlike
        // EventReminderService's EventReminderOptions POCO).
        await NotificationFlushService.FlushAsync(
            store,
            DateTimeOffset.UtcNow,
            mailer,
            localization,
            translationProvider,
            userInfo);

        // Re-schedule at the resolved admin cadence (NOT the baked default).
        // Read through U04's seam — it floors a missing LocaleSettings row to
        // 60, so the handler does NOT load the singleton or invent a floor
        // constant (single read path, the D6 shape).
        var minutes = await notifications.GetQuietCheckMinutesAsync();
        // The TimeoutMessage base takes a TimeSpan; constructing a fresh tick
        // with the resolved minutes makes Wolverine deliver the re-publish at
        // that runtime delay (the §6.4 self-reschedule, but with a
        // *resolved* cadence — see the divergence note below).
        return new[] { new NotificationFlushTick(TimeSpan.FromMinutes(minutes)) };
    }
}

/// <summary>
/// Durable recurring tick: flushes deferred notification emails.
/// Default baked delay 60 min (matches the QuietCheckMinutes default).
/// The handler re-schedules at the resolved admin cadence each run.
/// </summary>
/// <remarks>
/// <c>TimeoutMessage</c> is a <em>record</em> whose base constructor takes a
/// <see cref="TimeSpan"/> schedule (the <see cref="AuditPurgeTick"/> /
/// <see cref="EventReminderTick"/> precedent verbatim). M20 diverges in ONE
/// way: the delay is a *parameter* (default 60 min) so the handler can
/// construct a fresh tick at the resolved admin cadence each run — the
/// other three §6.4 jobs re-yield a fixed-baked tick because their cadence
/// is constant (1 day / 1 day / 365 days).
/// </remarks>
public sealed record NotificationFlushTick(
    TimeSpan delay = TimeSpan.FromMinutes(60))
    : Wolverine.TimeoutMessage(delay);
```

**Why the parameterized `TimeoutMessage` delay (the one sanctioned divergence
from the `EventReminderHandler` shape):**
- `Wolverine.TimeoutMessage` takes a `TimeSpan` in its base constructor.
  By making the tick a **parameterized record** (`TimeSpan delay` parameter,
  default 60 min), the handler can construct a **fresh tick with the resolved
  cadence** on each re-schedule.
- The three existing §6.4 jobs (AuditPurge 1-day, EventReminder 1-day,
  UsagePurge 365-day) re-yield a **fixed-baked** tick because their cadence
  is a constant — "re-yield the same message type carries the same schedule"
  is exactly the `AuditPurgeHandler` / `EventReminderHandler` precedent.
  M20's cadence is **admin-set at runtime** (`QuietCheckMinutes`, 5–1440), so
  the re-yield must carry the **resolved** delay — this is the deliberate
  point where M20 does **not** copy the precedent verbatim (the
  `AGENTS.md` "don't copy a common Marten/Wolverine pattern from memory"
  doctrine, applied to the one axis that genuinely differs).
- `QuietCheckMinutes` is read **through U04's seam**
  `NotificationService.GetQuietCheckMinutesAsync()` — which loads the
  `LocaleSettings` Marten singleton (U04's additive field) and **floors a
  missing row to 60**. The handler does **not** load the singleton itself or
  invent a floor constant — single read path, the D6 shape. It is **not** a
  static field and **not** an `IOptions` POCO.
- The `Program.cs` seed uses the **default** (60 min) — the first flush
  happens 60 min after boot; from the second run onward the handler reads
  the admin's live value each time.

### 2. `Program.cs` — seed the first tick

In the existing seed block (after the `UsagePurgeTick` publish, ~line 710),
add:

```csharp
// M20 (ADR 0121) — the deferred-notification email flush tick (the
// NotificationFlushHandler self-reschedules at QuietCheckMinutes after
// each run; this seed is the first-boot scheduling). The baked default
// is 60 min (matching QuietCheckMinutes default); the handler re-schedules
// at the resolved admin cadence from the second run onward.
await bus.PublishAsync(new NotificationFlushTick());
```

- **After host start** (`StartAsync` already done — this block is post-start).
- **In a scope** (`IMessageBus` is scoped — the `startupScope` already exists).
- **Idempotent:** the flush service is a no-op when no rows are due
  (U04's GATE-4 pin proves this). A double-schedule across two boots
  is harmless (same as the existing three §6.4 jobs).

### 3. DI check

- The handler is a **static class** — Wolverine discovers it via the
  `SideEffects` namespace scan (same as `EventReminderHandler`,
  `AuditPurgeHandler`). No explicit DI registration needed.
- The tick record is a **message type** — Wolverine discovers it as a
  message (the `TimeoutMessage` base makes it a scheduled message).
  No explicit registration needed (the existing three ticks are
  discovered the same way).
- **Verify** the handler's injected services are all registered in DI —
  `IDocumentStore`, `IMailerStage`, `ILocalizationService`,
  `ITranslationProvider`, `IUserInfoService`, `NotificationService` (all
  already registered — the M6 + M4 lanes register them; the
  `EventReminderHandler` injects the same set). **Note:**
  `IOptions<NotificationOptions>` is **not** injected by the M20 handler —
  the `FlushAsync` service reads its cadence from the `LocaleSettings`
  singleton (via `NotificationService.GetQuietCheckMinutesAsync`), not a
  config POCO (the D6 shape, unlike the M4 `EventReminderService` which
  takes `EventReminderOptions`).

### 4. Web pin tests (≥3, in `tests/Kumunita.Web.Tests/`)

- **Pin 1 — handler calls `FlushAsync` and re-schedules at resolved cadence.**
  Create a session with one `EmailDeferred == true` notification (quiet
  expired), call `NotificationFlushHandler.Handle(tick, store, mailer,
  localization, translationProvider, userInfo, notifications)` (the exact
  7-param signature above — no `IOptions`; `notifications` is the Core
  `NotificationService` used to read `GetQuietCheckMinutesAsync`), assert the
  notification's `EmailDeferred` is now `false`, and the returned
  `NotificationFlushTick` has a delay matching the `LocaleSettings`
  singleton's `QuietCheckMinutes` (set the singleton to a non-default value
  like 30 min via `SetQuietCheckMinutesAsync`, assert the tick's delay is
  30 min).

- **Pin 2 — no-op flush still re-schedules.**
  No deferred notifications, call `Handle`, assert the returned array has
  exactly one `NotificationFlushTick` (the job continues) and the tick's
  delay matches `QuietCheckMinutes`.

- **Pin 3 — `Program.cs` seed line present.**
  Read `Program.cs` source, assert it contains
  `PublishAsync(new NotificationFlushTick())` (the first-boot seed).
