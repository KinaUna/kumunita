### 2. `docs/adr/0120-guest-accounts.md`

The ADR (Status: **Accepted**). Match the ADR 0119 / ADR 0050 shape:

- `# ADR 0120 — Guest accounts (limited-privilege, time-bounded accounts on the M1 identity surface)`
- `**Status:** Accepted`
- `## Context` — the roadmap line (M19, the last milestone): "limited-privilege
  accounts for consultants, coaches, teachers, speakers, entertainers, etc.;
  admins set what a guest may access and when." The M1 identity surface
  (ADR 0001) already ships the thin-token / fat-authorization split and the
  `Verified`/`Blocked` additive standing fields; ADR 0050 already ships the
  admin-settled policy + one audited write lane + `/admin` controller shape.
  M19 adds the *outside* of the resident circle: a limited, bounded guest
  standing.
- `## Decision` — D1 (guest is a standing, not an entity) + D2 (the
  admin-settled, time-bounded `GuestAccess` document, one audited write lane)
  are the headline decisions; D3 (bounded window, no job), D4 (closed surface
  set, empty floor), D5 (the `Roles.Guest` claim mint, zero new authorization
  surface), D6 (the `/admin/guests` GlobalAdmin surface) are the supporting
  decisions. Cite ADR 0001-B (thin token / fat authorization), ADR 0030
  (composable roles), ADR 0004 §B.1 (additive surface), and ADR 0050 (the admin
  lane shape) as the seams this ADR rides.
- `## Consequences` — the named trade (a *coarse, closed* surface set for zero
  new authorization surface); the five deferred lanes (D7) are each a future
  ADR; the frozen `IAuthorizationService` seams, the audit log, and the resident
  standing are **unchanged** (C-M19·1/2/6).
- `## Supersedes` — none (M19 adds a standing; it does not supersede an earlier
  ADR — it *rides* ADR 0001-B / 0030 / 0004 / 0050). State this explicitly so a
  later reader knows M19 is an additive standing, not a correction.
