# M2 — Directory, profiles, groups

## Understanding
M1 shipped the **access model** (identity, groups, delegation, authorization, audit, side effects) and *stored* what M2 evaluates: `Profile.Visibility`, `Profile.ContactVisibility`, `Group` / `GroupMembership`, `DelegationGrant`. M2 adds the two resident-facing surfaces the design doc and `how-it-works.md` promise as "shared awareness" — **a directory of residents** and **a profile editor that controls who sees what** — plus **group management** so a profile's audience can point at a real named group (not only individuals). Per `ARCHITECTURE.md` §4.3, M2 introduces **no new authorization rule**; it routes every decision through the frozen `IAuthorizationService` and applies only a *candidate filter* (verified residents; unverified sees themselves) before invoking `CanSeeAsync`.

## Assumptions
- **No new documents.** M2 is surfacing + evaluation. `Profile`, `Group`, `GroupMembership`, `DelegationGrant`, `Audience` are all in `mt` from M1. No EF migration; no new `KumunitaFeature` step (or a no-op one, for the boot path). `M1DocTypes` conventions unchanged.
- **Authorization path is unique** (ADR 0006-D). M2's `DirectoryService` composes *existing* seams: `IUserInfoService` (read-only) + `IAuthorizationService` (single + bulk). It never reads `GroupMembership` / `DelegationGrant` for access decisions on its own.
- **Directory candidate filter (§4.3):** the *directory's* product query (not the authorization's rule) is "verified residents; an unverified viewer sees themselves; an unauthenticated viewer sees nobody". Applied *before* `CanSeeAsync`, never logged as an access decision. The *audience* decision on each included profile goes through `CanSeeAsync`.
- **Contact block gating (ARCHITECTURE.md §9):** `Profile.ContactVisibility: Audience?` gates email/phone display and is *evaluated only after* `Profile.Visibility` already allows the profile. `null` ⇒ hidden; non-null (including non-empty) ⇒ evaluate through `MatchGroups` (same-`Via` semantics; an explicit `Any` + empty grant still denies per invariant C1); a *viewing* user who is not allowed by `Visibility` never reaches the contact check (no row, no audit entry on the contact block — §9 pin).
- **`Profile` as `IAuditableResource`:** `Id = SubjectId`, `Name = DisplayName`, `OwnerId = SubjectId`, `Audience = Visibility`, `ComponentId = null`, `TargetKind = "directory"` (matches `ARCHITECTURE.md` §5's "directory" + ADR 0006 §C3). One new adapter, no new document shape.
- **M1's `UpsertProfileAsync(profile, patch)`** is the single write seam (M1 step 8 comment on `AccountController.Profile` confirms "null patches leave the row untouched"). M2's profile editor writes only through this.
- **`AccessAction` vocabulary:** M1 already defines `Read` and `Moderate`. M2 uses `Read` for the audience decision on profiles (a `read` on a `Profile` *is* "may I read this profile"). No new action id added. `DirectoryService` does not invent its own action id.
- **Group management UX scope (per user):** list + create + add/remove member. A moderator cannot manage groups (M1's ADR 0003 separation-of-duties holds: only the group owner or a GlobalAdmin reaches these methods). GlobalAdmin manages roles/audit/break-glass (M1's `/admin`) — M2 does not touch `/admin`.
- **View-as preview (per user):** the profile page offers a read-only "preview" mode that evaluates the current saved `Visibility` + `ContactVisibility` for the *author* themselves (i.e., "what I see of my own profile" — through the `Owner` branch, trivially `Allowed`; the interesting case is *other residents*, which requires a separate `as` selector that evaluates the same saved values as if the actor were a chosen sample resident). To keep scope honest: **M2 ships a "how I appear" preview (self-viewing, the one branch that is always `Allow`) and an "as [specific resident]" selector for residents the author can resolve** — both read-only, no write path.
- **Tests:** the M1 design's "run result + accept gate + FACES" pattern is the acceptance model. M2 follows the same: a step-by-step plan, then run and record the three tests against the design doc's acceptance gate.

## Approach
Three work tracks, sequenced. **Track A (Core):** `DirectoryService` — composition over M1 seams (list, detail, view-as, contact-block evaluation; all through `IAuthorizationService` only) + `ProfileToAuditableResource` adapter + `IUserInfoService.GetProfilesAsync(verifiedOnly)` read seam (the one new read method, non-breaking per ADR 0006-E compatible lane). **Track B (Web):** DirectoryController (`/directory` list + `/directory/[subjectId]` detail) + ProfileController (replace the M1 profile page: name/email + `Visibility` editor + `ContactVisibility` opt-in block + "view-as preview"); GroupsController (`/groups` list + `/groups/new` + `/groups/[id]` with add/remove member). **Track C (Tests):** the M2 invariant-anchored seam list (contact-block never-on-hidden, candidate-filter-vs-authz, directory audit row shape, group add/remove audit lane, delegation on a profile, group ownership / non-author / group member / GlobalAdmin / unverified-viewer decision matrix) + e2e + the record gate.

Every step ends with build green. The last unit (U15) is the final recorded handoff (not a test run — that lives in U11).

## Workflow — handoff protocol for fresh-context agents

This milestone is executed as a sequence of **sealed units** (U1…U15 below), one unit per fresh agent with a ~64K context window. Each unit is **self-contained**: given *only* the design doc + its entry read-list + one prior handoff-note line, the unit can be completed and verified without re-reading the full M2 plan.

**Shared state (the three-tier contract):**
- **Primary — the design doc** (`docs/design/m2-directory-profiles-groups.md`, written in U1/U2). Every unit cites invariants/seam names from this doc, never from memory of the M1 conversation. U1/U2 pin the exact C# signatures of every seam U3–U14 must match; if a later agent finds a mismatch, the design doc wins and the agent updates it in the same commit (the drift-guard below).
- **Secondary — this file** (`docs/plans-milestones/plan-m2-directory,-profiles,-groups.md`) — the unit registry with each unit's deliverables and exit criteria.
- **Scratch — the rolling handoff note** (`docs/plans-milestones/m2-handoff-notes.md`). One section per unit, appended (never rewritten). Each unit writes exactly one short section before it exits; the next unit reads only that section + its own entry read-list.

**Per-unit template** (each `U` below follows this):
- **Goal** — one sentence, one or two related deliverables.
- **Entry reads** — the *minimal* file list to open (3–5 files, all <~300 lines each). No full-repo scan. The design-doc section the unit cites is named explicitly.
- **Deliverables** — a closed set of new or modified files (≤ 4 files per unit, ~≤ 600 LOC combined). No "misc cleanups" outside the deliverables list.
- **Exit** — `run_build` green for the touched project(s) **+** the named unit-level test(s) pass (if any) **+** the handoff-note section is appended. The full test suite runs *only* in U11 (acceptance gate) and U12 (e2e); no other unit runs anything beyond its own unit tests.
- **Drift guard** — if a unit finds a signature or behavior in the design doc that does not match the code, it **updates the design doc in the same commit** (not the reverse). Each unit is the *defining* unit for the seams it introduces and must pin their exact C# signatures in the design doc before finishing. If a unit discovers an M1 seam it depends on is not what it expects, it **stops** and writes that finding into its `Deviations` line rather than silently patching M1 — that is a `record_observation`, not a unit completion.

**Handoff-note format** (append a `## U<n> — <unit title>` section, each one ≤ 15 lines):
```
Shipped:      <file paths changed/created>
Signatures:   <the public API shapes this unit defines, e.g. `Task<IReadOnlyList<Profile>> GetProfilesAsync(bool verifiedOnly)`>
Deviations:   <any place doc and code disagree; name the doc line, code line, and which won; or "none">
For next:     <one concrete thing the next agent must not break or must build on>
```

**Rules that keep context small (enforced by the unit boundary, not the agent):**
1. A unit never modifies a file it is not listed on in its own deliverables (if it *must* touch one to make an exit criterion green, add the file to the deliverables list *and* name it in `Deviations`).
2. A unit never rewrites the design doc wholesale — at most it rewords its own section (its defining seams) in place.
3. Handoff notes are append-only. A later unit may not delete an earlier unit's section; it may append a `## U<m> — correction to U<n>` line if it discovers an unrecorded deviation.

## Risks & Open Questions
- **`IUserInfoService.GetProfilesAsync` is non-breaking but *is* a new method added to a frozen interface.** ADR 0006-E's *compatible* lane explicitly allows adding methods (the `IDocumentSession` overloads on `IAuthorizationService` are the precedent — a *new* method on a frozen interface, not a change to an old one). Still, keep the signature minimal and the doc-comment anchored to the same invariants (C3, C4, C6); the M2 design doc must name it as M2's *one* addition, with the rationale spelled out.
- **Profile enumeration vs. privacy** — `GetProfilesAsync(verifiedOnly=true)` returns every verified profile's *document*. This is the *candidate set* for the directory, not a visible set. The directory page renders only what `CanSeeAsync` surfaces; the rest is hidden (count visible in the aggregate row, names/values never rendered). Make sure the view model for the directory is a projection of `VisibleSet.Visible` × `Profile` — never an enumeration of `Profile`'s own fields for a hidden row.
- **Unverified self-sight** — an unverified resident seeing only themselves: this is the §4.3 candidate filter, *not* the `IAuthorizationService`'s concern. If it leaks into `CanSeeAsync` it will be mis-audited as an access decision; keep it in `DirectoryService`.
- **View-as preview is a read-only *preview* — do not accidentally let it be a write surface.** M2's "view-as" is a `GET` that evaluates the saved values as if the *author* were the viewer (or a chosen resident); no state change.
- **`ContactVisibility` truth table at `null` vs. `Any`+empty vs. `Any`+one-grant vs. `All`+empty** — M1's C1 test pins the *directory* behavior; M2 explicitly pins *each* of those four `ContactVisibility` shapes against a `Visibility` that already allowed the profile (this is the "contact block never on a hidden profile" test, `ARCHITECTURE.md` §9).
- **M2 adds no Wolverine side effects.** M1's `OutboxEmailHandler` / `AuditPurgeHandler` stay as-is; M2 does not add a new email surface (no "you now appear in the directory" email — M3+). If M2 introduces any new side effect, it would be via M1's `IMailerStage` seam; M2 is read-and-edit, not send.
- **Open question (resolved by user):** the view-as preview is *read-only self- or chosen-resident*, not a write path; M2 ships it as a *separate* action (`PreviewViewAs`), not an editor field.
- **Open question (for M3+):** does the directory surface a "who is in a group" UI? M2's GroupsController is *per-group* (owner + members), not directory-level; directory-level group browsing (e.g., "groups I'm in") is M2 only if it reuses existing seams, otherwise M3. M2 includes **only** the group detail + member management that the profile editor needs.
