# M23 · U01 — `Profile.Bio` + `Profile.TagIds` additive fields + `ProfileUpdate` extension

**You are the U01 agent.** This is a **Core** unit. It adds exactly **two
additive POCO fields** to the M1-registered `Profile` doc (`Kumunita.Core.
UserInfo`) and **two additive optional trailing fields** to the `ProfileUpdate`
patch record — nothing else. It does **not** extend `UpsertProfileAsync` (U02),
create `IProfileFindService` (U03), or touch the Web project. **Exit:
`dotnet build Kumunita.slnx -c Debug` clean + `Kumunita.Core.Tests` green.**

**Read the design doc first** — it locks the C# in this unit (D1/D3,
C-M23·1/C-M23·5/C-M23·6). If the design doc's §2.1/§2.2 C# differs from
anything you find in the codebase, **the codebase wins for mechanics** (naming,
file layout, `using`/namespace, the `Audience` type's actual namespace) and the
design doc wins for the **locked surface** (the two additive fields, the
`null` ⇒ don't-touch patch rule, the `Tag.Id` reference idiom).

## Goal

Make the `Profile` doc carry a **biography** (a `string?` rich-content field)
and **author-set tags** (a `string[]` of `Tag.Id` values) — **additive** fields
on the **existing** doc (ADR 0004 §B.1 — delta-detected, idempotent, **no
re-seed**, **no new `*DocTypes` surface**, **no new document**), and extend the
`ProfileUpdate` patch record so the two fields are **writable** through the
existing single write lane (D3). **Zero new authorization surface** (C-M23·2).

## Deliverables (2)

### 1. `src/Kumunita.Core/UserInfo/Profile.cs` — two additive fields

Add the two fields to the `Profile` POCO, **after `EmailLanguage`** (so the
additive fields stay grouped at the end, the `AvatarId`/`TimeZone`/`DateFormat`/
`EmailLanguage` shape), each with an ADR 0004 §B.1 doc-comment (the
`TimeZone`/`DateFormat`/`EmailLanguage` comment shape):

```csharp
/// <summary>
/// The resident's **biography** (M23, ADR 0123 D1/D5) — the rich-content body
/// (Markdown + optional in-content images, the ADR 0025/0031 shape), rendered
/// on the directory detail by the single <c>MarkdownRenderer.RenderHtml</c>
/// helper. Stored as the authored Markdown <c>string</c>; <c>null</c>/empty
/// means "no bio" (the detail renders no bio block, C-M23·5). Gated by
/// <see cref="Visibility"/> (C-M23·1, D2 — the M2 "kept for the detailed
/// fields" audience finally takes over). An **additive** field (ADR 0004
/// §B.1), like <see cref="EmailLanguage"/>: delta-detected, idempotent, no
/// re-seed, no EF migration.
/// </summary>
public string? Bio { get; set; }

/// <summary>
/// The resident's **author-set tags** (M23, ADR 0123 D1/D3) — the
/// <c>string</c> <see cref="Tags.Tag"/> ids the resident picked (skills,
/// interests, knowledge, expertise). References the **frozen ADR 0044 shared
/// <c>Tag</c> doc** by <c>Tag.Id</c> — the <see cref="Posts.Post.TagIds"/> /
/// <see cref="Pages.Page.TagIds"/> idiom verbatim (a third referencer of the
/// same doc, **not** a new tag type, C-M23·6/D1). Default empty (a profile
/// with no tags). A tag is a **label, never a gate** (C-TG·1 carried to
/// profiles, C-M23·6). An **additive** field (ADR 0004 §B.1), like
/// <see cref="EmailLanguage"/>.
/// </summary>
public string[] TagIds { get; set; } = [];
```

> Match the **exact** `string[]` default-empty idiom the `Post.TagIds` /
> `Page.TagIds` field uses (read `Post.cs` / `Page.cs` and copy the field shape
> + comment style so the two are consistent).

### 2. `src/Kumunita.Core/UserInfo/Profile.cs` — `ProfileUpdate` extension

Extend the `ProfileUpdate` record with **two additive optional trailing
fields** (the `Address = null` precedent — appended with defaults so existing
positional call sites compile unchanged; `null` ⇒ don't touch, the patch rule
every field follows):

```csharp
public sealed record ProfileUpdate(
    string? DisplayName,
    string? Email,
    string? Phone,
    Audience? Visibility,
    Audience? ContactVisibility,
    /// <summary>The resident's address (see <see cref="Profile.Address"/>). Appended with a
    /// default after the frozen M1/M2 five-field shape so existing positional call sites
    /// compile unchanged; null leaves the current value untouched (the "null ⇒ don't touch"
    /// patch rule every other field follows).</summary>
    string? Address = null,
    /// <summary>The resident's biography (see <see cref="Profile.Bio"/>). M23 (ADR 0123 D3)
    /// — the rich-content body. Appended with a default after the frozen six-field shape so
    /// existing positional call sites compile unchanged; null leaves the current value
    /// untouched (the "null ⇒ don't touch" patch rule).</summary>
    string? Bio = null,
    /// <summary>The resident's author-set tags (see <see cref="Profile.TagIds"/>). M23
    /// (ADR 0123 D3) — the list of <see cref="Tags.Tag"/> ids (the create-or-get resolve is
    /// U02's). Appended with a default after the frozen seven-field shape so existing
    /// positional call sites compile unchanged; null leaves the current value untouched.</summary>
    IReadOnlyCollection<string>? TagIds = null);
```

> **Do not** change the existing five frozen positional fields' order or
> types — only **append** the two new fields with defaults (D3, the
> `Address` precedent). The `UpsertProfileAsync` lane that *consumes* these is
> U02's, not this unit's.

## Tests (Core)

Add/extend the `Kumunita.Core.Tests` profile test (the existing profile /
`UserInfo` test file):

- **A profile round-trips the two new fields.** Store a `Profile` with a
  `Bio` and a `TagIds` array; reload; assert `Bio` is verbatim and `TagIds`
  equals the stored array. (The ADR 0004 §B.1 additive round-trip.)
- **`ProfileUpdate` carries the two new fields with defaults.** A positional
  call site using the old five/ six-field shape still compiles; a new
  `ProfileUpdate` with `Bio` + `TagIds` set reflects them. (The `Address`
  appended-with-default precedent.)
- **`null` ⇒ don't-touch patch shape.** A `ProfileUpdate` with `Bio = null` and
  `TagIds = null` is distinguishable from one with them set (the patch rule).

> These are **shape** tests (the fields exist, the defaults hold, the patch
> carries them). The *write-lane* behavior (bio verbatim, tag create-or-get,
> no profile-write audit row) is **U02's** — do not test it here.

## What this unit must NOT do (the §drift-guard)

- **Must not** create a `ProfileBio` / `ProfileTag` document, a new
  `*DocTypes` surface, a new relational table, or a second `Tag` doc type for
  profiles — D1 / C-M23·6 forbids it (the `Tag` is the frozen ADR 0044 shared
  doc; the bio is a field on the `Profile`).
- **Must not** store the bio as a separate doc, or add a `BioDocTypes` surface
  — the bio is a `string?` field on the `Profile` (D1).
- **Must not** add a per-field audience (a distinct audience for the bio vs.
  the tags) — both are gated by the **one** existing `Profile.Visibility`
  (D2 / C-M23·1); the audience is already on the doc, this unit adds no new
  one.
- **Must not** extend `UpsertProfileAsync` here — the write lane is **U02's**
  (this unit owns only the two fields + the patch record).
- **Must not** change the existing `ProfileUpdate` positional field order or
  types — only **append** the two new fields with defaults (D3).
- **Must not** create a new `IUserInfoService` write method for bio/tags — it
  rides `UpsertProfileAsync` (D3); and **must not** touch the Web project (the
  editor is U04's).
