**You are the U00 agent.** This is a **docs-only** unit: it authors the design
doc and ADR 0122, and it locks the register's [PROPOSED] set (D1–D9,
C-M21·1…C-M21·7, FACES F1–F5, the closed `kw-l` key set, the §gate acceptance

The design doc and ADR must lock, verbatim, the register's [PROPOSED] set:
D1–D9, C-M21·1…C-M21·7, FACES F1–F5, the closed `kw-l` key set (the
§"closed `kw-l` key set" table in the register), the §gate acceptance tests
(GATE-1…GATE-6), and the §drift-guard. If a D# or invariant is wrong,
   **amend it here** (and note the amendment in the handoff notes) — do not
   defer the amendment to a later unit. Two named amendment surfaces to
   verify against the live codebase:
   - **D5's exact upload standing** (the register flags this as the amendment
     surface): confirm `GlobalAdmin ∪ Moderator` is the intended set, or
     widen/narrow per ADR 0017.
   - **C-M21·7's "one audit row" on the upload**: the register's C-M21·7 text
     says the upload "appends exactly one `AccessAudit` row," but the
     codebase convention (verified in `AttachmentController.Upload`,
     `PostService.CreatePostAsync`, the `Announcements` write lane) is that
     **writes do not emit audit rows** — only reads do (the frozen
     `IAuthorizationService` audits `Read` decisions; the standing check on the
     upload is the Web boundary's, not a `Read` decision). **Resolve this in
     §1.a**: either keep the codebase convention (the upload is a standing-gated
     write, **no** audit row — matching `PostService.CreatePostAsync`) and note
     C-M21·7 as amended to "one standing-gated write, no audit row," or state
     explicitly that M21's upload *does* emit a row and show the seam that
     produces it. U02/U03 implement whichever you lock.
