**The [PROPOSED] lock set (from the register — lock these **verbatim**):**

- **D1 — One new bounded context `Kumunita.Core.PersonalNotes`, two
  documents, one new surface.** `PersonalNote` (`OwnerId`, `TargetKind`,
  `TargetId`, `Body`, `FolderId?`, `Tags`, `Created`, `Modified?`) +
  `NoteFolder` (`OwnerId`, `ParentId?`, `Name`), on a **new
  `PersonalNotesDocTypes`** surface (the M17 `BookmarkDocTypes` shape —
  additive, idempotent, zero migrations). `TargetKind` is a **string**
  restricted to the closed set
  {`post`, `grouppost`, `event`, `page`, `project`, `todo`, `board`,
  `document`, `directory`} — the exact vocabulary the existing
  `*ToAuditableResource` adapters already emit. *Forbids:* a separate
  document per surface; a `PersonalNote`-per-kind set of tables; an enum
  type for `TargetKind`; a migration of an existing surface; reusing the
  M17 `Bookmark` doc (M37 is a *new* context — the M17 surface is
  untouched).
- **D2 — A personal note is a personal-by-id record, never an audience
  decision.** No adapter, no new `AccessAction`/`AccessVia`/`Decide()`
  branch, no new method on `IAuthorizationService` (the M17 `Bookmark` /
  M9 ADR 0105 shape). The owner's own note list is a personal read (like
  the M6 inbox / M17 bookmark list): no `CanSeeAsync` pass over the note
  rows. A non-owner (a `GlobalAdmin` included) gets a non-leaky **404**
  that commits **no** `AccessAudit` row either. *Forbids:* a
  `PersonalNoteToAuditableResource`; running the owner's own list through
  `IAuthorizationService`.
- **D3 — Note-attaching requires visibility; note-attaching grants
  nothing.** The write lane re-runs the target's frozen `Read` decision
  (`CanAsync(Read)` over the target's existing adapter — the *same call
  the detail page uses*) and refuses **404** (not 403; no Deny row
  survives, the M16 create-gate posture) when the target is not visible.
  The note row itself never appears in, widens, or is consulted by any
  `CanSeeAsync` pass anywhere. *Forbids:* a note on an invisible target;
  a note consulted by any read decision; a `GlobalAdmin` peek branch.
- **D4 — A note is *content*, not a pointer: it carries a body, and the
  body is owned by the author.** `PersonalNote` carries `Body` (the
  resident's own writing, stored as raw text, Markdown-rendered on read
  via the **frozen** `MarkdownRenderer` — the M31 / ADR 0031 shape) +
  `Modified` (the body's revision witness). M17's `Bookmark` has **no**
  body; M37's `PersonalNote` **does**. The body is **never** mutated in
  place — edit is a **new revision** (the M14 / M16 author-only lane); the
  body is **visible to the author always** — even when the target is gone
  (the D7 degraded shape). *Forbids:* a `Bookmark`-shaped `PersonalNote`
  (no body); a body that mutates in place; a body not visible to the
  author when the target is gone.
- **D5 — Tags are author-set, free-form, per-note; the tag set is
  normalized on write.** A note's `Tags` is an `IReadOnlyList<string>`
  (or a JSON column — U01's call, mirroring the codebase's existing
  list-of-strings shape). On write, each tag is **lowercase, trimmed,
  deduped, sorted** (the M26 `Tag` doc's `Name` normalization shape, the
  idempotency witness). A tag is **not** a platform-wide `Tag` doc (the
  M26 tag lane is a *shared* vocabulary; M37's tags are *personal* labels
  — different shapes, different surfaces, different invariants — U00
  records the distinction in the design doc §2.1 doc-comment). *Forbids:*
  a `PersonalNote` that references the M26 `Tag` doc's `TagId`; a tag set
  that is not normalized; a tag that is platform-visible.
- **D6 — The folder tree is a personal tree, bounded in depth, unique in
  name.** Each resident has their own tree of `NoteFolder` rows, keyed on
  `OwnerId` + a bounded `ParentId` (depth ≤ 2: root → child →
  grandchild). A folder's `Name` is unique within the owner's tree (the
  `(OwnerId, ParentId, Name)` unique index is the witness). A note's
  `FolderId` is the **owner's** folder id (a note cannot live in another
  resident's folder). A folder's deletion **moves** its notes to the root
  (`FolderId = null`) — the note body is never lost. *Forbids:* an
  arbitrary-depth folder tree; a folder `Name` that is not unique within
  the owner's tree; a note that lives in another resident's folder; a
  folder deletion that removes note bodies.
- **D7 — The list degrades, never leaks; the note body survives the
  target's death.** A note whose target is absent, soft-deleted, or no
  longer visible renders the **generic** `pn.list.degraded` label (a
  closed `kw-l` key) — **no title, no link, no id** — and the note's
  **body remains visible** to the owner (the D4 "content, not pointer"
  pin). The note controls (edit / move / tag / delete) still work on the
  degraded row — none of them require the target's own read seam. *Forbids:*
  a 404/403 on a dangling note row; leaking a removed target's title; a
  note body not visible to the owner when the target is gone; a per-row
  `CanSeeAsync` branch in the list beyond the owning surface's existing
  seam.
- **D8 — M37 is a standing core surface, not a lane: no off-by-default
  toggle.** No admin toggle, no `LocaleSettings`-style switch, no
  `KumunitaFeature` admin flag. *Forbids:* an off-by-default admin toggle
  for M37; a `LocaleSettings`-style switch.
- **D9 — The close flip is one atomic unit (U06) — the six-member close
  flip.** M37 is the **last** milestone on the roadmap (no `M38` to
  promote). U06 flips `Milestones.cs` M37 `StatusNext` → `StatusDone`
  (and **no** `M38` row); `MilestonesTests.cs` re-pinned to the
  **"last milestone, no successor"** pin; the README **Roadmap** (M37 →
  done) + the M37 **Status** line; `docs/STATUS.md`;
  `docs/ARCHITECTURE.md`'s value-chain table gains the **M37 row**;
  **and** `src/Kumunita.Web/WhatsNew.cs` gains the **M37 entry** (the
  **required sixth member** — ADR 0110). All six ship **in the same
  unit**. *Forbids:* reordering M37; adding an `M38` row; editing a
  shipped milestone's text; breaking the `MilestonesTests` pins; flipping
  one surface and not the others; **omitting the `WhatsNew.cs` entry**.

- **C-M37·1 … C-M37·8** — verbatim from the register.
- **FACES F1–F5 + the named trade** (the register's wording): F1 the note-
  attach is atomic and idempotent (the `(OwnerId, TargetKind, TargetId)`
  unique index is the witness — the M17 `Bookmark` shape); F2 the write
  lane is the target's own frozen decision (invisible target ⇒ 404, no
  note row, no Deny row surviving); F3 the list is the owner's personal
  read (zero audit, zero `CanSeeAsync` over the rows); F4 a dangling note
  degrades, never leaks — and the **body survives** (the
  `pn.list.degraded` closed key, no title/link/id; the note controls still
  work); F5 a standalone core surface (D8). **Named trade:** the note
  body's permanence vs. the dangling-target leak surface — the row
  survives its target's death (a silently-removed note is worse than a
  greyed-out one), and the leak surface of a dangling row is exactly
  **one static `kw-l` string** + the author's own body (which is visible
  to the author always by D4).

- **§kw-l key list** (the `pn.*` keys × en/de/fr/da — U05's source of
  truth): `pn.nav`, `pn.list.title`, `pn.list.empty`,
  `pn.list.degraded`, `pn.list.kind.post`, `pn.list.kind.grouppost`,
  `pn.list.kind.event`, `pn.list.kind.page`, `pn.list.kind.project`,
  `pn.list.kind.todo`, `pn.list.kind.board`, `pn.list.kind.document`,
  `pn.list.kind.directory`, `pn.note.edit`, `pn.note.delete`,
  `pn.note.move`, `pn.note.tag.add`, `pn.note.tag.remove`,
  `pn.note.attach`, `pn.note.attached`, `pn.folder.new`,
  `pn.folder.rename`, `pn.folder.delete`, `pn.folder.empty`. (Adjust names
  to the views as you author them; the **list** is what U05 registers —

- **§gate — the three acceptance tests** (U06 adds them):
  (a) **closed-loop** (a resident attaches a note to a post they can see
  → it appears in their `/notes` list under the `post` group with the
  body rendered → they edit the body (a new `Modified` timestamp) → they
  add a tag (the tag set is normalized — lowercase, trimmed, deduped,
  sorted) → they move the note into a folder they created (the
  `(OwnerId, ParentId, Name)` unique index is the witness) → they delete
  the note → it is gone; a second attach of the same target is a **no-op**
  — one row, one `Created`);
  (b) **handoff-authorization-boundary** (attaching a note to a post the
  resident *cannot* see ⇒ 404, no note row, no Deny row surviving; a
  `GlobalAdmin` who is not the owner of a note list gets a 404 with
  **no** `AccessAudit` row — the C-M37·2 zero-audit personal read);
  (c) **part-vs-whole-audit-completeness** (the owner's own list load
  commits **zero** `AccessAudit` rows — C-M37·2 — while the *write*
  lane's single `CanAsync(Read)` check is the target's own frozen decision
  (C-M37·3): the part (one attach) and the whole (the list) audit
  differently by design, and both pins hold together).

- **§deferred:** the "nudge the author on note" notification lane (a

  stats; note **search** (a follow-on lane, own ADR); the **platform-wide

- **§drift-guard — the frozen pins + the drift log:** the frozen seams
