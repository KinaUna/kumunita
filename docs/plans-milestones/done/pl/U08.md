# U08 — Project picker on to-do / board edit forms + project link on their detail views

**Goal:** wire the **existing** M5 to-do + board surfaces to the new
`Project` association: the **project picker** `<select
name="ProjectId">` on the to-do + board **edit** forms (and, per the M5
composer convention, the new forms too — see Deliverables) + the
**project link** on `TodoDetail.cshtml` / `BoardDetail.cshtml` (D9 —
`pl.todo.project_link` / `pl.board.project_link`, rendered **only**
when the to-do / board's `ProjectId` resolves to a readable,
non-soft-deleted project — the D6 dangling-association rule). The
association **save** goes through the U04 `SetTodoProjectAsync` /
`SetBoardProjectAsync` seams (a **separate** POST, not folded into the
existing M5 update POSTs — the frozen M5 `UpdateTodoRequest` /
`UpdateBoardRequest` DTOs are **untouched**). **`dotnet build` + `npm
run build` clean; Web tests pass; all M5 pins still pass** (the
additive-surface pin).

**Entry reads:** U07's handoff section (the project detail / composer
exist + the `pl.project.*` keys + the `ClearGoal` convention + `dotnet
build` clean); `docs/design/pl-goals-projects-design.md` §5 (the
project-link wire on to-do / board detail — the D9 placement) + §9.1
(the `pl.todo.project_link` / `pl.board.project_link` keys this unit
registers);
`src/Kumunita.Web/Views/Projects/Edit.cshtml` + `Create.cshtml` (the

`src/Kumunita.Web/Views/Projects/BoardEdit.cshtml` +
`BoardNew.cshtml` (the **real** board edit / new forms — same);
`src/Kumunita.Web/Views/Projects/TodoDetail.cshtml` +

insertion point, the existing `canEdit` / action-button block shape the

`src/Kumunita.Core/Localization/KnownTranslationKeys.cs` (the `pl.*`
keys registered so far — this unit adds its own set only).

**Deliverables (7 files touched / created):**
- `src/Kumunita.Web/Models/TodoEditorModel.cs` (edit): additive fields
  — `ProjectId?` (the current association, for the select's
  `selected`), `ProjectOptions` (the `List<(string id, string title)>`
  shape `ParentOptions` uses — the audience-surfaced **projects**,
  via `ListProjectsAsync` — the `ParentOptions` seed convention,
  verbatim) + the detail-view's link field (`ProjectId?` +
  `ProjectTitle?` + `ProjectUrl`) — the existing M5 fields are
  **not renamed / reordered / removed** (the frozen-M5 view-model
  pin).
- `src/Kumunita.Web/Models/BoardEditorModel.cs` (edit): the same
  additive `ProjectId?` + `ProjectOptions` (the board detail's
  link-field equivalent).
- `src/Kumunita.Web/Controllers/ProjectsController.cs` (edit):
  - the to-do edit / new + board edit / new **GET** actions seed
    `ProjectOptions` (the `ParentOptions` seed convention —
    `ListProjectsAsync` audience-surfaced, the standing `actorId`
    from `KumunitaPrincipal`) + the current `ProjectId` from the
    loaded to-do / board doc;
  - **two new POST actions** — `TodoSetProject(string todoId, [FromForm]
    string? projectId, ...)` → `SetTodoProjectAsync`, and
    `BoardSetProject(string boardId, [FromForm] string? projectId,
    ...)` → `SetBoardProjectAsync`; each is a **standalone** form POST
    (its own small form on the edit page — **not** the main M5 update
    form), redirects back to the to-do / board detail on success
    (the M5 "POST-redirect-GET" convention); the service's standing
    re-check + project guard (U04) is the enforcement — the controller
    does no standing math (the frozen ADR 0006 split);
  - the to-do / board **detail** GET actions resolve the linked
    project for the D9 link: when `ProjectId != null`, call
    `GetProjectAsync` (U03) — on 404 / 403 the link field is **left
    empty** (the D6 dangling rule — the link is not rendered, no
    error surfaced to the user).
- `src/Kumunita.Web/Views/Projects/Edit.cshtml` (edit): a new
  **card** (the `rc-editor` / picker card convention) with the
  **project picker** — a `<select name="ProjectId">` (the `ProjectOptions`
  + a leading unassigned option — the `ParentId` select shape,
  verbatim convention) + a small standalone `<form method="post"
  action="/projects/todos/@id/set-project">` wrapping the select + a
  save button (`pl.todo.set_project` key); the existing M5 form +
  its `action=` target are **untouched**.
- `src/Kumunita.Web/Views/Projects/Create.cshtml` (edit): the **same**
  project-picker card, **mirroring the existing `ParentId` select**
  (line ~98-107: `@if (Model.ParentOptions.Count > 0)` → the
  `<select name="ParentId">` + unassigned option) — a
  `<select name="ProjectId">` + unassigned option, the same
  `@if (Model.ProjectOptions.Count > 0)` gate, the same card convention;
  the form's existing `action=` POSTs to the M5 `TodoCreate` action,
  which maps `ProjectId?` into the (additively-extended) `CreateTodoRequest`
  (see the frozen-DTO note below) — the to-do is created **with** its
  initial project association in one POST, exactly the way the M5
  composer already creates a to-do with its initial `ParentId`.
- `src/Kumunita.Web/Views/Projects/BoardNew.cshtml` (edit): the same
  project-picker card, the board-side equivalent of the above (the
  board's create form is the association entry point for the board's
  `ProjectId`, mirrored the same way).
- `src/Kumunita.Web/Views/Projects/TodoDetail.cshtml` +
  `BoardDetail.cshtml` (edit): the **project link** (D9) — when the
  view-model's link field is non-empty, a small link row / chip
  (the existing detail-view's metadata-row convention) labeled
  `pl.todo.project_link` / `pl.board.project_link` linking to
  `/projects/projects/{id}` (U07 — real); **absent** when the field
  is empty (the D6 rule — no empty link, no "unknown project"
  text).
- `src/Kumunita.Core/Localization/KnownTranslationKeys.cs` (edit):
  the `pl.todo.project_link`, `pl.todo.set_project`,
  `pl.board.project_link`, `pl.board.set_project` keys this unit
  uses — **all four languages** (en/de/fr/da parity — the
  `KnownTranslationKeysTests` four-language pin).

**Sequencing note:** this unit **modifies** four existing M5 views
(`Edit.cshtml`, `Create.cshtml`, `BoardEdit.cshtml`,
`BoardNew.cshtml`) + two M5 detail views (`TodoDetail.cshtml`,
`BoardDetail.cshtml`) — **additively only** (new cards / rows /
fields; no existing markup, field, route, or DTO shape changed). The
M5 create DTOs gain a **single additive** `ProjectId?` field on
`CreateTodoRequest` + `CreateBoardRequest` (mirroring the M5
`ParentId` composer convention — `Create.cshtml` already carries a
`ParentId` select, confirmed), + the matching additive `ProjectId`
write in `ProjectService`'s create lanes (the standing re-check is
**not** re-run for the create-time write — the author's standing on
create is self-evident, the ADR 0001-B shape). **The** M5
`UpdateTodoRequest` / `UpdateBoardRequest` DTOs are **untouched** —
the edit-time association save goes through the **separate** U04
`SetTodoProjectAsync` / `SetBoardProjectAsync` seams (the standalone
POST forms on the edit views, **not** folded into the existing M5
update POSTs), and the U04 association seams themselves are **not
re-signed** by this unit. No existing M5 field is renamed / reordered
/ removed anywhere in this unit (the frozen-M5-surface pin).
