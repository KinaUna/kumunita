- `## 3. The design decisions` — each **[PROPOSED]** until U01 locks them:
  - `### 3.1 Zero Core change (D1)` — no seam, no document field, no schema,
    no seeding, no EF, no new audit row shape; the `ListInRangeAsync` seam is
    reused unchanged (it is already window-agnostic); the only additive C# is
    2 additive view-model fields (+ `MonthLabel`→`Label`) + the `?view=`
    param.
  - `### 3.2 The `?view=` selector + per-view window (D2)` — `?view=day|week|month`
    on the existing route (no new route); the window computed in the
    controller (day = anchor day; week = anchor's Monday-start week; month =
    anchor's calendar month); `month` is the default; an invalid/out-of-set
    value falls back to `month` (a display fallback, not an error).
  - `### 3.3 Day + Week as time-ruler grids (D3)` — hour rows (the
    `00:00`–`24:00` ruler, rendered server-side) + event blocks positioned by
    `%` top/height within the day column (computed client-side in the new
    `events-calendar-time.ts` over the authorized chip list); Multi-day events
    repeat per touched day (the same `[startUtc, endUtc)` interval rule as
    Month).
  - `### 3.4 Month reframed to a true calendar month (D4)` — the anchor's
    calendar month as a 5–6 week × 7 day grid; the existing chip-distribution
    + overlap logic (unchanged `events-calendar.ts`) is reused as-is because
    it is view-agnostic (it iterates whatever day-columns exist).
  - `### 3.5 The Day/Week/Month toggle + navigation (D5)` — the three view
    buttons in the header (each a plain GET link with `?view=`); prev/next
    shift the anchor by the **view's unit** (±1 day / ±1 week / ±1 month),
    `?view=` + `componentId` ride along; today resets to the zone's today.
  - `### 3.6 The `kw-l` keys (D6)` — exactly 3 new keys
    (`events.calendar.view.day/.week/.month`) × 4 languages; the view labels
    (full date / date range / month name) are computed display strings, not
    registry keys.
  - `### 3.7 Out of scope (future lanes) (D7)` — no create/RSVP/drag from the
    calendar (detail page owns RSVP; ADR 0063 D7 unchanged), no iCal (M6), no
    recurrence model, no year view, no multi-event column packing /
    overlap-lane algorithm (overlapping blocks render side-by-side/stacked —
    a display nicety, future lane), **no week-start resident override**
    (platform default is Monday; a per-resident override is a new surface →
    future lane), no new notifications, no server-side overlap or
    time-positioning API (client-side display concerns).
  - `### 3.8 The invariants (pinned)` — C-DWM·1 … C-DWM·9 (the 9 invariants
    below).
- `## 4. Invariants (pinned for EV-DWM)` — the 9 invariants, each with a
  one-line EV-DWM note (C-DWM·1 zero Core change; C-DWM·2 same visibility;
  C-DWM·3 `?view=` is a display selector; C-DWM·4 overlap + time-positioning
  are client-side display concerns; C-DWM·5 week starts Monday + zone is
  display-only; C-DWM·6 nav is plain GET links by view-unit; C-DWM·7 plain
  TS / EV-CAL module untouched; C-DWM·8 backward-compatible / default month;
  C-DWM·9 localization parity).
- `## 5. FACES (pinned, 8)` — F1 day shows only the anchor day; F2 week shows
  the anchor's Monday-start week; F3 month shows the anchor's calendar month
  (5–6 weeks); F4 default (no `?view`) is month; F5 an invalid `?view` falls
  back to month; F6 prev/next/today shift the anchor by the view's unit and
  preserve `?view=` + `componentId`; F7 a day/week/month page leaks nothing a
  feed page would not; F8 the `?view=` selector + window are never an access
  input.
