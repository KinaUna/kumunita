# M28 U04 — The `TimeLimitMiddleware` + `Program.cs` registration + the `?error=time-limit` login landing + the middleware tests

## Context (self-contained)

M28 = **Guardian time limits**: a **guardian** sets a per-child schedule
(hours × days-of-week, Blocked/Allowed polarity) that **gates the child's
whole-platform access** (a sign-out, the `BlockedAccountMiddleware` analog).
This is the **inverse of the M20 quiet lane** (ADR 0121) but on the **GU
guardian surface** (ADR 0028), using the **same pure-evaluator discipline**
(wall-clock-first, ADR 0019). U00 locked the design doc + ADR 0151. U01
created the doc + enum. U02 authored the pure evaluator. U03 added the three
seams + implementation.

**U04 ships the enforcement gate** — the `TimeLimitMiddleware` (the exact
`BlockedAccountMiddleware` shape) + its `Program.cs` registration (after
`BlockedAccountMiddleware`) + the `?error=time-limit` code on
`AccountController.Login` (the `?error=blocked` precedent) + the 3 F6
middleware tests. **This is the lane's headline mechanic** (C-M28·1/C-M28·5):
a restricted child is **signed out** (all routes), lands on a distinct
"you're outside your allowed hours" message. **Zero new authorization
surface** (the middleware does **not** call `IAuthorizationService` — it
calls `GetActiveTimeLimitAsync` + `IsAllowedNow`, the C-M28·2 pure-function
discipline).

**The middleware shape (the `BlockedAccountMiddleware` analog):**
- Anonymous → pass.
- Resolve the subject (the `ClaimTypes.Subject` claim, the
  `BlockedAccountMiddleware` shape).
- `IUserInfoService.GetActiveTimeLimitAsync(subject)` → `null` /
  `Enabled == false` → pass (the floor, C-M28·3).
- Resolve the subject's **effective zone** (the ADR 0019 chain: the
  `Profile.TimeZone` override → the platform default → UTC floor — the
  `EffectiveTimezoneResolver` / `EventReminderService.TryResolveZone`
  shape).
- `GuardianTimeLimitEvaluator.IsAllowedNow(schedule, now, zone)` → `true`
  → pass; `false` → `SignInManager.SignOutAsync()` + redirect
  `/Account/Login?error=time-limit` (the **distinct** code — not
  `blocked`).

**The `?error=time-limit` landing (the `?error=blocked` precedent):**
`AccountController.Login` GET has an error-code switch (the
`"blocked"` code maps to a `kw-l` key). U04 adds the `"time-limit"` code
to the same switch, mapping to a new `kw-l` key
(`account.time_limit.login_message` — U05 lands the key; U04 references
it, the `?error=blocked` precedent in the same switch).

## Rules

- **Zero new authorization surface** (C-M28·5) — the middleware does
  **not** call `IAuthorizationService`, does **not** add a `Decide()`
  branch, does **not** add an `AccessAction` or `AccessVia`. It calls
  `GetActiveTimeLimitAsync` (the U03 seam) + `IsAllowedNow` (the U02 pure
  function) + `SignInManager.SignOutAsync` (the existing ASP.NET
  `SignInManager`).
- The middleware runs **after** `BlockedAccountMiddleware` (a fully-blocked
  account hits the `blocked` landing first — the M28 time-window layer is
  the **second** gate, not the first).
- The `?error=time-limit` code is **distinct** from `?error=blocked` (the
  child sees a different message — "outside your allowed hours" vs
  "account suspended").
- The zone resolution is the **child's** effective zone (C-M28·6, ADR
  0019) — not the guardian's zone, not UTC (unless the child has no
  override + the platform has no default → UTC floor).
- The middleware is a **per-request** check (one `mt` round-trip — the
  `BlockedAccountMiddleware` cost profile) — no background job, no
  scheduled flush (unlike M20's cadence — M28 has no held-email to release).
