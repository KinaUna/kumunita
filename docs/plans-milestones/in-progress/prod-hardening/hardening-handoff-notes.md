## F2.U1 — Part-0 design pin
- **Landed:** `docs/design/prod-hardening-f2-token-hash.md` (new, §1–§9). **No code, no build, no `.cs` touched.**
- **Hash choice (pin §2):** **SHA-256** over UTF-8 bytes → **hex, 64 lowercase** chars (exactly `^[0-9a-f]{64}$`). One static helper **`Sha256Hex`** (≤ ~10 LOC). Rationale: tokens are high-entropy secrets (32 random bytes), so a one-way hash suffices — this is **not** the F6 argon2id password lane.
- **Storage (pin §3):** **reuse the existing `IdentityToken.Token` column — NO new column, NO schema change.** Stored value becomes the digest. `Id` stays the stable handle; only the `Id` travels in a verify URL.
- **Write path (pin §4):** verify mint `NewVerifyToken` (`:1514`, `:1519`) → `Token = Sha256Hex(NewSecret())` (raw discarded — verify URL carries `Id`). Setup mint `FirstBootSeeder.cs:~274` → `Token = Sha256Hex(token)` (raw stays in email/env, operator types it into the form).
- **Backward-compat rule CHOSE (pin §6): *Accept-legacy-via-dual-compare*.** A pre-upgrade non-64-hex cleartext row is accepted on read *in the lane that presents it as-is*; never used in a lane that presents the raw (clause 2 only fires on a genuine match). **This deliberately DEVIATES from the plan's recommended "reject non-64-hex" rule** — that rule is **not implementable** in the pinned scope without breaking the verify lane (which presents the *stored* value) or locking the operator out of first-boot setup, and would force a new column / Web change (both forbidden). Residual is **bounded + self-limited**: verify tokens self-expire ≤ `Verification__TtlDays` (default 14); every **new** mint is hashed (the actual AUTH-02 goal). **Open item for the owner (NOT assumed):** if zero residual is wanted, the follow-up is a one-time re-mint (new hashed rows + invalidate old) — needs a migration/owner step, **out of F2 scope**.
- **Drift / scope notes (pin §8, NOT silently resolved):**
  1. **DUAL-MODE read path (the big one).** The plan assumed `FindTokenAsync` always gets a raw secret — **false.** The verify lanes (`:256` `VerifyWithTokenAsync`, `:310` `VerifyAndSetPasswordAsync`) present the **stored column value** (Web does `session.LoadAsync<IdentityToken>(id)` by `Id` and passes `token.Token`); only the setup lane (`:1251`) presents the **raw**. The pin's exact rewrite (§5) is a **dual comparison** `t.Token == presented || t.Token == presentedHash` — the **only** Core-only rule that keeps both lanes working with no new column / no Web change. **GOTCHA:** `presentedHash` MUST be precomputed as a local constant BEFORE the query (Marten can't translate `SHA256.HashData` into SQL) — do not put `Sha256Hex(...)` inside the `.Where(...)`.
  2. **Setup mint is a second file.** Plan scoped F2.U2 to "`IdentityService.cs` only," but the setup write (`FirstBootSeeder.cs:~274`) is outside that. To hash it, **U2 must also touch `FirstBootSeeder.cs`** (one line) and make `Sha256Hex` `internal` (shared, not duplicated). **Flagged to owner:** leaving the setup mint cleartext defeats half of AUTH-02. If the owner insists on one file, the setup mint becomes a separate follow-up unit — **record as an open item, do not drop it.**
  3. **"Raw goes in the URL" (plan framing)** is only true for the **setup** lane; the **verify** lane puts the **`Id`** in the URL and the raw is a discarded throwaway (pinned accurately §4a).
- **Pinned test names (U4 implements, pin §7):** `VerifyToken_StoredHashedNotCleartext`, `VerifyToken_ConsumedOrExpiredStillRejected`, `VerifyToken_ExistingCleartextRowHandled` (the last **documents** the §6 accept-legacy behavior — it is the single source of truth for that decision).
- **Open items (owner, NOT assumed done):** (a) zero-residual re-mint follow-up (§6); (b) U2's extra `FirstBootSeeder.cs` file / setup-mint scope (§8.2).
- **Drift pause:** none — but §8.1/§8.2 are **divergences from the plan's stated scope/read assumption**, recorded for the owner before U2 proceeds (not a codebase-drift stop, a design decision + scope flag).
