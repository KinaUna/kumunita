**The locked decisions you implement (from the design doc — read the
§gate + §drift-guard sections verbatim):**
- **C-M37·4 / F1** — the **closed-loop gate**: attach a note to a
  visible post → the `/notes` list shows the row under the `post` group
  with the body rendered → edit the body (a **fresh** `Modified`
  timestamp, one row — the D4 "content, not pointer" witness) → add a
  tag (the tag set is normalized — lowercase, trimmed, deduped, sorted
  — the D5 pin) → move the note into a folder (the
  `(OwnerId, ParentId, Name)` unique index is the witness — the D6
  pin) → delete the note (the row is gone, the body is gone — the M17
  `Bookmark` physical-removal shape) → a second attach of the same
  target is a **no-op** (one row, one `Created` — the F1 / C-M37·4
  witness — the unique index is the idempotency pin).
- **C-M37·2 / C-M37·3 / F2 / F3** — the **handoff-authorization-
  boundary gate**: attaching a note to a post the resident *cannot* see
  ⇒ 404, no note row, no Deny row surviving (the M16 create-gate
  posture); a `GlobalAdmin` who is **not** the owner gets a non-leaky
  **404** on both the `GET /notes` list and the `GET /notes/has/...`
  query, and **no** `AccessAudit` row commits on either (the C-M37·2 /
  F3 pin — the ADR 0105 "operator has no read standing" precedent); the
  note row never grants anything to a later read.
- **C-M37·2 / C-M37·5** — the **part-vs-whole-audit-completeness
  gate**: the owner's own list load commits **zero** `AccessAudit` rows
  and runs **zero** `CanSeeAsync` passes over the note rows (the M6-
  inbox / M17-bookmark personal-read shape); the D3 write-lane check is
  the **target's own** frozen `Read` decision (one decision, the
  target's own row — not a note row).
- **C-M37·8 / D9** — the **close flip is atomic (the six-member close
  flip)**. M37 is the **last** milestone on the roadmap (no `M38` to
  promote — the M36·10 / M35·11 framing, re-applied). The six surfaces
  ship **in the same unit** (the M36 close-flip precedent).
