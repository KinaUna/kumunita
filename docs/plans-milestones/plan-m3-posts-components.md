# M3 — Posts, component lists, (deferred report flow) — sealed unit register

## Understanding
M2 shipped shared awareness (directory + profile editor + groups) and introduced no new documents or authorization rules. M3 delivers the next how-it-works.md promise — "Post and discuss. Announcements and conversations, organized into topics like Safety, Maintenance, Social, and Governance" — as product: the **signal** surfaces. Per the scope decision, M3 ships **posts (create + list + detail), one-level threaded replies, and component-organized feeds**. Report-driven moderation (file / assign / unlock / resolve) is **deferred to M3b**, though the `Report` *document* is registered in M3's storage step for forward compatibility. Moderation surfaces and the audited `Via = Report` read branch are explicitly out of M3 scope.

This is the **first content milestone**: M2 was pure surfacing over M1's stored documents; M3 introduces **new domain documents** (`Post`, `PostReply`, `Report`), a **new versioned step** (`M3DocTypes`), a **new bounded context** (`Kumunita.Core.Posts`), and **one new read seam** on a frozen interface (`IUserInfoService.GetComponentsAsync(bool)` — the ADR 0006-E compatible lane, mirroring M2's `GetProfilesAsync` ADD). That is why M3, like M2, begins with a two-part design doc (U1/U2) that pins every seam, invariant, and test name before any unit implements — the guard against *Distributed fragmentation* and *Accidental integration*.

## Assumptions
- **Scope (per user):** M3 = posts (create/list/detail) + one-level threaded replies + component-organized feeds. **Out of scope → M3b:** the report workflow (file, assignee, resolve), the report-driven moderator unlock, the `Via = Report` read branch on content, and moderator surfaces (queue, resolve UI). M3 ships **no moderation actions** and does not touch `/admin` (M1's admin surface unchanged).
- **`Report` table registered but dormant.** M3 registers the `Report` document/table (per the Q3 answer) for forward compatibility but exposes **no surface and no tests** for it — its workflow is owned by M3b. This resolves the Q1↔Q3 tension: *table in M3, flow in M3b*.
- **One-level thread.** `PostReply` has `PostId` but **no `Audience` field**; a reply is visible iff its parent `Post`'s `Read` decision is `Allowed`. **No `IAuditableResource` for replies; no second `CanSeeAsync` call** (the C-M3·1 invariant).
- **Components are organizational buckets, not access boundaries.** A post in "Safety" is visible exactly per its own `Audience`; the component is a *feed filter* (which list it lands in), never an authorization rule. Pinned by C-M3·2; mirrors M2's C-M2·2.
- **Authorization path is unique (ADR 0006-D; C6; C3).** `PostService` composes *only* `IAuthorizationService` (+ its own Marten session) and the frozen `IUserInfoService` read seams. It never reads `GroupMembership`/`DelegationGrant` for its own access decisions. Feed = one aggregate audit row (`targetKind "post"`, `visibleCount`/`hiddenCount`); detail = one row per decision. Same-transaction via the frozen `IDocumentSession` overloads (C3).
- **Single ADD on a frozen interface (ADR 0006-E compatible lane), mirroring M2's U3 `GetProfilesAsync`:** `Task<IReadOnlyList<Component>> IUserInfoService.GetComponentsAsync(bool enabledOnly)` — a read lane for the composer's *component picker*. Read only, no audit row. The composer's *audience* selector reuses M2's existing `GetGroupsForUserAsync`/`GetGroupIdsAsync` — no new seam needed there.
- **Versioned storage step (ADR 0004 §B.1).** M3's documents are **Marten-native** (POCOs, conventional string `Id`), registered in a new parallel surface `M3DocTypes.Configure(StoreOptions)` (analogous to `M1DocTypes`), delta-detected + idempotent, **no seeding** (the four components already exist via M1's seeder). M3 does **not** get a hand-rolled `FeatureSchemaBase` (that carve-out is reserved for operator-written tables like `AdminOverride`). *Open veto:* if a distinct `FeatureSchemaBase` subclass is preferred, flip it before U3.
- **No new outbound channel.** M3 is intake (signals in), like M2 — the only channel is M1's verification email; notification surfaces are M6. A post/reply commits atomically with its audit row (C3) but stages **no** email.
- **`AccessAction` vocabulary.** M1 defines `Read` + `Moderate`. M3 exercises `Read` on a `Post` (feed + detail). `Moderate` on a post is **reserved for M3b**; M3 adds **no** new action id.
- **Test model (unchanged).** The M1/M2 acceptance gate (three-test shape: closed-loop / handoff / part-vs-whole) + invariant-anchored seam-test list pinned in the design doc's Part 2, recorded in a rolling handoff note.

## Approach
Three tracks, sequenced — exactly like M2. **Track A (Core):** `Kumunita.Core/Posts/` — the three documents, the `PostToAuditableResource` adapter, `PostService` (feed, detail, create, reply — all routed through `IAuthorizationService`), `GetComponentsAsync` on `IUserInfoService`, and the `M3DocTypes` registration. **Track B (Web):** `PostsController` (`/community/{componentId}` feed, `/posts/{id}` detail + replies, `/posts/new` compose), view models, Razor under `Views/Posts/`, and nav. **Track C (Tests):** invariant-anchored seam list (pinned in Part 2) + the three-test acceptance gate + the M3b deferral close.

Every unit ends with **build green**. The last unit (U12) appends the final handoff section and the M3→M3b deferral note so M3b's M1-style OOS close will be honest.

## Workflow — handoff protocol for fresh-context agents

This milestone is executed as a sequence of **sealed units** (U1–U12 below), one unit per fresh agent with a ~64K context window.

**Shared state (three-tier contract):**
U1/U2 pin the exact C# signatures of every seam U3–U12 must match
- **Secondary — this file** (`docs/plans-milestones/plan-m3-posts-components.md`) — the unit registry with each unit's deliverables and exit criteria.
- **Scratch — the rolling handoff note** (`docs/plans-milestones/m3-handoff-notes.md`). One section per unit, appended (never rewritten). Each unit writes exactly one short section before it exits; the next unit reads only that section + its own entry-read list.

**Per-unit template** (each `U` below follows this): **Goal** (one sentence, one or two related deliverables); **Entry reads** (the minimal file list, 3–5 files <~300 lines each, no full-repo scan; the design-doc section cited is named); **Deliverables** (a closed set of new/modified files, ≤ ~4 files / ~600 LOC, no misc cleanups); **Exit** (`run_build` green for the touched projects; handoff-note entry appended *before* any follow-up action).

**Unit-series rules:** (1) a unit never modifies a file not in its own `Deliverables`; (2) never rewrites the design doc outside the §2.7 drift-guard; (3) never introduces a test whose exact name is not in the §2.5 seam list; (4) never opens a *new* seam on `IUserInfoService` / `IAuthorizationService` / `IIdentityService` beyond what U1/U2 pinned; (5) never re-shapes a document (`Post`, `PostReply`, `Report`) outside the §2.2 pin; (6) if entry reads reveal the design doc is out of date, the unit pauses and records `## U<m> — Drift pause` in the handoff note.
